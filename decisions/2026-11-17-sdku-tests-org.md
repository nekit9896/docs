# Решения по организации sdku_tests (аудит чата 2026-11-17)

Статус: принято. Источник: интервью (grilling) с владельцем проекта.
Область: репозитории `docs`, `hydro-backend-tests`, `sdku-test-tools` (проект `evoscada`).

## Контекст

Автотесты для двух микросервисов Гидроуклона (часть СДКУ ЭВОСКАДА, нефть в
трубопроводах) плюс системные тесты. Текущее состояние: есть только
документация (разрозненная), кода практически нет. Этот журнал — аудиторский
след: «от чего к чему пришли».

## Принятые решения

| # | Решение |
|---|---|
| D1 | Каноническое имя продукта — **Гидроуклон** (латиница `hydroslope`). «Гидроклон» — опечатки, исправлять. |
| D2 | Источник истины по тест-кейсам — тест-планы (`docs/test-plans/`). `roadmap_coverage` — устаревший черновик; его переработка и сроки этапов — **в самом конце** финализации документации. C4 — по старым диаграммам, переработать (реальность бэкенда может отличаться). |
| D3 | Канонические URL репозиториев — за переменной/плейсхолдером; корпоративные URL в открытые документы не выкладывать. |
| D4 | Политика тестов: **интеграционные** — реальные подключения к стенду (один микросервис + его хранилища); **системные** — связка сервисов через Kafka/WS/HTTP; **E2E/сценарные** — полный путь «действие → расчёт → аларм → конечная точка бэкенда» **без UI-автоматизации**. Все тесты запускаются из CI/CD. Локальная машина — только для написания кода (запуск/отладка — в корпоративной системе). |
| D5 | `.clinerules` **версионируются в git** (убрать из `.gitignore`): единый каркас 00–04 для всех репозиториев, минимальные пер-репо различия. Правило: версии зависимостей — в `pyproject.toml` / `poetry.lock`. |
| D6 | Границы репозиториев: `sdku-test-tools` — только доменно-независимое (клиенты Kafka/Redis/HTTP/WebSocket/SSH/Docker, generic-фикстуры, утилиты); `hydro-backend-tests` — всё доменное (сценарии, фикстуры, тестовые данные, конфигурация стенда, маркеры pytest). Инструменты не знают про Гидроуклон. |
| D7 | Потребление инструментов: `sdku-test-tools` публикуется как **wheel в корпоративный Nexus (private PyPI)** и подключается зависимостью в `pyproject.toml` с фиксацией версии; локально — editable/path-установка. |
| D8 | Docker: образ `hydro-tests-runner`, Dockerfile в `hydro-backend-tests`; база `python:3.12-slim` через Nexus-proxy; venv по `poetry.lock`; тег = версия `pyproject.toml` + короткий hash `poetry.lock`; пересборка — при изменении `poetry.lock`/`pyproject.toml` или вручную. Пайп делает `docker pull` из Nexus Docker Registry. |
| D9 | CI: пайпы выполняются **GitLab CI** в проекте `evoscada` (секреты и переменные — GitLab CI variables); Bitbucket — мастер-хостинг, GitLab — зеркало + CI. Триггеры пайпов пока **не фиксируем** (не согласовано с разработчиками). |
| D10 | Структура `docs`: рабочие документы разложены по каталогам (`architecture/`, `services/`, `test-plans/`, `roadmap/`), исходники Confluence — в `docs/confluence/` с правилом синхронизации (рабочие доки — источник истины). Имя репозитория остаётся `docs`. |
| D11 | Журнал решений — `docs/decisions/`: каждое существенное решение отдельной записью. |
| D12 | Привязка тестов к кейсам тест-планов: маркер `@pytest.mark.case_conflu("HY-CALC-014")`. Базовый `@pytest.mark.case(...)` зарезервирован за TestOps (его отзеркаленные сценарии). |
| D13 | `.env` / `.env.example`: владелец имён переменных стенда — `hydro-backend-tests`; `sdku-test-tools` — только универсальный загрузчик. Секреты — из GitLab CI variables, значения в git не попадают. |
| D14 | Архитектура автоматизации по образцу `C:/Users/nekit/PycharmProjects/training`: слои клиенты → модели (датаклассы/pydantic) → конфиги/датасеты → сценарии → функции тестов (декорирование/запуск) → утилиты; conftest — общий + отдельный у интеграционных и системных. |
| D15 | `pyproject.toml`/`poetry.lock` в `docs` остаются («без разницы»). Модель веток — не регламентируется. README всех репозиториев — переписать (UTF-8, роль, структура, ссылка на карту `docs`). |
| D16 | `HY-HIST-043` удалён на ревью — это норма; перенумерация не нужна. Фактически действующих кейсов HY-HIST — **48** (001…049 без 043). |
| D17 | Roadmap актуализируется (фаза 4): HY-CALC = **85**, HY-HIST = **48**; мусорная ссылка на `HY-HIST-050` — удалить; плейсхолдеры «X» — заменить реальными цифрами. Числа берём из тест-планов. |
| D18 | «Заглушка» в системном плане — временная метка «сценарий ещё не проработан»; проработка постепенная. |
| D19 | Требования без кейсов (`R-HYDR-011, -015, -044, -045, -047, -048, -049, -071, -077`) — кейсы вслепую НЕ заводим; ждём реестр требований. |
| D20 | CI-расписание: системные — по расписанию (ночной прогон); интеграционные/сценарные — возможность запуска из пайпа. Точные триггеры — после согласования с разработчиками. |
| D21 | Flaky-политика: авто-ретрай 1 попытка в CI; повторное падение → скип + ОБЯЗАТЕЛЬНАЯ задача на починку. |
| D22 | Ожидания — только waiters (polling/события), без `time.sleep`; дефолтный таймаут **10 с**, уточнение — явно в конфиге сценария; таймауты — единые константы. |
| D23 | Каталог тестовых данных — **`datasets/`** (не `test-data/`). Генерация данных (фабрики/префиксы) и политика очистки — отложены, по факту практики. |
| D24 | Стенд — развёрнутый тестовый стенд с непрерывным потоком данных; рабочая область — **собственные тестовые ТУ** (технологические участки); выполнение тестов — последовательное (один стенд). |
| D25 | Структура отчётности Allure (epic/feature/story) и процесс триажа падений — НЕ фиксируем сейчас (не актуально). |
| D26 | Инструменты качества кода: **black + isort + flake8**; mypy — не применяем; в CI тест-репозиториев — линт-джоба на каждый MR; ревью тестового кода — вручную, как продуктового. |
| D27 | Тест-дизайн: использовать классы эквивалентности, граничные значения, таблицы решений (режимы), state-machine (сессии). **Сценарии документации ≠ количество тестов**: тест-планы — сборник логики по кейсу, 1 кейс → N тестов (повтор `case_conflu` — норма); массовое переписывание сценариев не делаем. Матрица покрытия/KPI/версионирование wheel — по мере надобности. |

## Отложено

- Реестр требований к Гидроуклону и матрица покрытия требований — позже; кейсы по
  требованиям без реестра не заводим (D19). Матрица покрытия/KPI — по мере надобности (D27).
- Сроки этапов роадмапа — в конце финализации документации.
- Согласование триггеров CI/CD с разработчиками — до фиксации в `.gitlab-ci.yml` (D20).
- Полная актуализация C4 — по фактическим диаграммам бэкенда.
- Генерация тестовых данных (фабрики/уникальные префиксы) и политика очистки — по факту практики (D23).
- Структура отчётности Allure и процесс триажа падений — не фиксируем (D25).
- Версионирование wheel `sdku-test-tools` — по мере надобности (D27).
