## Профиль исполнителя и калибровка оценок

- Исполнитель: мидл-автоматизатор (Python, pytest), предметку знает слабо.
- 1 SP = 2 часа. Минимум задачи — 2 ч (1 SP); предпочтительно ≤ 1 дня (4 SP); максимум на сложную объёмную задачу — 2 дня (8 SP).
- Ставки за кейс: простой — 2 ч (1 SP), средний — 4 ч (2 SP), сложный — 8 ч (4 SP).
- Погрешность оценок времени задач — **±30%** (как снижаем — см. «Точность оценок»).
- Готовность: `недели = Σчасов / 40` при FTE = 1.0 (полное погружение, только тесты). Календарные даты не фиксируем (D27).

## Общий смысл и подход

Весь объём тестирования разбит на три горизонта. Каждый решает свою задачу, и вместе они дают полное покрытие без дублирования.
```
┌──────────────────────────────────────────────────────────────┐
│  Слой 1: Интеграционные                                      │
│  Что: сценарии на входе и выходе микросервиса                │
│  Как: HTTP-ручки, запись в Redis (вход), чтение из           │
│        Redis, Kafka (выход)                                  │
│  Когда: при каждом push, при ручном запуске                  │
│                                                              │
│  ➜ Проверяем: отправили данные в микросервис —              │
│    получили ожидаемый результат. Изолировано,                │
│    понятно где искать причину падения.                       │
└────────────────────┬─────────────────────────────────────────┘
                     │
┌────────────────────▼─────────────────────────────────────────┐
│  Слой 2: Системные                                           │
│  Что: взаимодействие 2–3 микросервисов целиком               │
│  Как: Kafka, WebSocket, Redis, HTTP ручки всех сервисов      │
│  Когда: при merge в develop, ночные, ручной запуск           │
│                                                              │
│  ➜ Проверяем: цепочка данных проходит от одного сервиса     │
│    к другому. Формат, таймауты, контракты.                   │
└────────────────────┬─────────────────────────────────────────┘
                     │
┌────────────────────▼─────────────────────────────────────────┐
│  Слой 3: E2E / сценарные                                     │
│  Что: полный путь от действия диспетчера до данных на экране │
│  Как: WebSocket (подписка на поток), HTTP, Redis,            │
│        конечная проверка через hmi-backend и alarm-view      │
│  Когда: перед релизом, ручной запуск, ночные                 │
│                                                              │
│  ➜ Проверяем: всё вместе работает как ожидает пользователь. │
└──────────────────────────────────────────────────────────────┘
```

## Контроль здоровья сервисов в setup

Перед каждым тестом — проверка, что все микросервисы живы.
Это попытка обратиться к эндпоинту диагностики и получить ответ, что микросервис готов обрабатывать запросы - так мы подтверждаем, что тесты имеет смысла зпаускать.
```
SERVICES = {
    "hydro-calculation":     "http://hydro-calculation:8080/actuator/health",
    "hydro-history-model":   "http://hydro-history-model:8080/actuator/health",
    "hmi-backend":           "http://hmi-backend:8080/actuator/health",
    "alarm-service":         "http://alarm-service:8080/actuator/health",
    "alarm-view":            "http://alarm-view:8080/actuator/health",
    "clickhouse":            "http://clickhouse:8123/ping",
    "redis":                 "http://redis:6379",
}
```

## Работа с тестовыми данными на общем стенде

Стенд <STAND_HOST> — общий. Другие пользователи работают, данные меняются. Тесты не могут чистить всё подряд.
**Стратегия:** резервируем конкретные технологические объекты и трубы для автоматизации. Это реальные объекты из информационной модели — просто те, которые закреплены за тестами.
Задачи:

*   подготовить базовый набор тегов, договориться с командами о неприкосновенности тестируемых тегов (задачи 0.16, 0.19 / old 5.2)

### 2.6. Watermark и прогресс

**Сценарии:** HY-HIST-035…038 (4)
| Проверка | Что | Формула |
| --- | --- | --- |
| Монотонность | `wm1 ≤ wm2 ≤ wm3` | Каждый следующий ≥ предыдущего |
| STALLED → MOVING | Блокировка → разблокировка | `state`: 1→2→1 |
| Прогресс | `p1 ≈ 5%, p2 ≈ 10%, p3 ≈ 15%` | `((wm - start)/(target - start)) × 100` |
| ETA | `etaSeconds = (target - wm) / speed` | Остаток реального времени |

### 2.7. Отказоустойчивость

**Сценарии:** HY-HIST-039…042 (4)
| Сценарий | Что эмулируем | Ожидаем |
| --- | --- | --- |
| Buffer Overflow | Поток > bufferSize | Событие BUFFER_OVERFLOW, messagesDropped > 0 |
| Failover (RAFT) | Kill лидера (2 экз. mod-hist) | Перевыбор ≤ 15 с, сессия не потеряна |
| hydro-calc не отвечает | Kill hydro-calc | SESSION_ERROR через 30 с (confirmTimeout) |
| Retry после ERROR | Восстановление hydro-calc | Sессия возвращается в RUNNING с того же watermark |

## Точность оценок и снижение погрешности

Погрешность — это погрешность оценок времени реализации задач (не измерений в самих тестах). Базовая — **±30%**: исполнитель не знает предметку глубоко, стенд незнаком, часть API — по допущениям.

Методы снижения:

1. Ревизия ставок 2/4/8 ч по факту первых задач этапа 1 (тесты калькуляций пишутся первыми — они же калибруют ставки) → цель **±15%**.
2. План-факт по этапам: фиксация фактических часов после каждого этапа и пересчёт остатка.
3. Ревизия ставок после каждой группы задач, когда группа больше 8 SP.
4. Авточек-листы стенда (0.13–0.15) снимают отладку стенда из оценок кейсов.
5. Переиспользование клиентов lds-autotest: в оценках 0.3–0.9 учтена адаптация, а не написание с нуля.
