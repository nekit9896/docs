# Research: Автоматизированные тесты гидрорасчёта (Гидроуклон)

**Date**: 2026-11-18 | **Spec**: [spec.md](./spec.md) | **Plan**: [plan.md](./plan.md)

Phase 0: все неопределённости Technical Context разрешены; открытые вопросы стенда сведены в R9 и не блокируют проектирование.

## R1. Стек: Python 3.12+ и pytest

- **Decision**: Python 3.12+, pytest как тестовый раннер; зависимости — через `pyproject.toml` (venv).
- **Rationale**: профиль исполнителя (Python, pytest, см. docs/plans/automation-roadmap.md), совместимость с кодовой базой lds-autotest; маркировка, параметризация и JUnit XML из коробки покрывают FR-006/FR-008.
- **Alternatives considered**: Robot Framework (слабая типизация, труднее переиспользовать Python-клиенты стенда); unittest (нет маркировки и отчётов из коробки).

## R2. Клиенты стенда: lds-autotest как библиотека (без копирования кода)

- **Decision**: подключать модули lds-autotest как зависимость (git/pip); в проекте — тонкие адаптеры и фикстуры поверх них.
- **Rationale**: задача 0.26 роадмапа; единый источник исправлений клиентов (SSH, Kafka, Redis, HTTP, WebSocket, Docker, ClickHouse, PostgreSQL — задачи 0.3–0.9).
- **Alternatives considered**: форк/копирование клиентов в проект (расхождение версий, двойное обслуживание); написание клиентов с нуля (задвоение задач 0.3–0.9).

## R3. Связь «тест ↔ кейс»: один тестовый модуль на кейс каталога

- **Decision**: именование `tests/<suite>/test_<CASE-ID>_<slug>.py`; CASE-ID (например, `HY-CALC-012`) — часть имени модуля и маркера; параметризация — только внутри одного кейса.
- **Rationale**: трассировка FR-007; простая карта покрытия FR-012; независимый запуск и вердикт кейса FR-006/FR-004.
- **Alternatives considered**: один parametrized-тест на весь набор (смешение вердиктов, сложнее отладка); декларативные YAML-кейсы (преждевременно, сложнее отлаживать).

## R4. Ожидания и синхронизация

- **Decision**: единый слой ожиданий (waiters): событийные (WebSocket), поллинг (HTTP/Redis/БД), чтение Kafka с таймаутом ≥ 30 с; повторы (retry) — только на инфраструктурные ошибки (недоступность стенда), не на расхождения поведения.
- **Rationale**: edge cases spec: недоступность стенда ≠ провал поведения (FR-004); конкретные окна ожидания задаются правилами исполнения кейсов.
- **Alternatives considered**: фиксированные sleep-паузы (нестабильность, SC-004); повторы на любые ошибки (маскировка дефектов).

## R5. Состояние стенда и изоляция прогонов

- **Decision**: фикстуры очистки состояния (function/session scope) и восстановление начального состояния перед прогоном (задачи 0.11/0.12); закреплённые тестовые теги MT1.LU1/MT1.LU2 (0.19); блокировка стенда на время прогона (семафор в окружении) с явным сообщением — FR-010.
- **Rationale**: воспроизводимость FR-005/SC-003; один выделенный стенд — риск пересечения прогонов.
- **Alternatives considered**: отдельный стенд на каждый прогон (ограничения инфраструктуры); полагаться на ручную дисциплину расписаний.

## R6. Отчётность и трассировка

- **Decision**: JUnit XML (нативно pytest → TestOps, задача 0.23) + JSON-отчёт прогона по контракту `contracts/report-schema.md` с полями `run_id`/`case_id`/`verdict`/`mismatches`; вердикты: `passed`/`failed`/`skipped`/`infra_error`.
- **Rationale**: FR-004/FR-007/FR-008 и SC-005 (причина провала без чтения кода).
- **Alternatives considered**: только Allure (требует сервера, избыточно); вывод в stdout (не машиночитаем).

## R7. Конфигурация окружения

- **Decision**: единый env-конфиг (задача 0.25): адреса/порты/каналы обмена/учётные имена — в `config/env/*.yaml`; секреты — из переменных окружения или менеджера секретов, не в git.
- **Rationale**: открытые вопросы стенда (R9) переезжают в конфиг без правок кода; Assumptions spec.
- **Alternatives considered**: хардкод адресов в коде (противоречит 0.25); .env-файлы в репозитории (риск утечки секретов).

## R8. CI и качество кода

- **Decision**: пайплайн (задача 0.24): статические проверки Python (ruff, mypy постепенно), ночной полный прогон по расписанию и запуск по требованию; провал кейса блокирует качества-гейт — FR-013.
- **Rationale**: SC-002 (ночное окно), SC-004 (стабильность).
- **Alternatives considered**: только ручной запуск (не выполняет FR-009/FR-013).

## R9. Открытые вопросы стенда (НЕ блокируют проектирование)

- hot topic ↔ `model_main_{id}`, схемы ClickHouse `history` и PostgreSQL `sessions`, порты 8379/8432/8443, имена топиков Kafka — уточняются после развёртывания стенда (задачи 0.1/0.2/0.25).
- **Decision**: все адресуемые параметры выносятся в env-конфиг (R7) с placeholder-значениями и TODO; до уточнения зависимые проверки помечаются `skip` с указанием причины.
- **Rationale**: Assumptions spec; неопределённость учтена погрешностью оценок ±30% (роадмап).
