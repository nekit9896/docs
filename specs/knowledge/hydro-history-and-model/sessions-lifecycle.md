# Сессии: жизненный цикл

Сущность Сессии — таблица `session_manager_sessions`, номер присваивается при
создании (KB-HM-STORAGE-001).

## Статусы Сессии (из readme.md)

| Статус | Описание |
|---|---|
| `CREATED` | Сессия создана, в процессе инициализации |
| `PAUSED` | Сессия активна, занимает ресурсы, поддерживается её жизнеспособность |
| `CLOSED` | Сессия закрыта, ресурсы освобождены |
| `SAVING` | Сессия в процессе сохранения |
| `SAVED` | Сессия сохранена |

Статусы сохранятельных сессий (другая сущность) — в KB-HM-SAVE-001.

## Создание Модельной сессии (POST)

1. Создаём сущность Сессии, присваиваем номер (`session_manager_sessions`).
2. Сессия в статусе `CREATED`.
3. Создаём Владение процессом в Watermark-сервисе (таблица `watermarks`,
   KB-HM-WATERMARK-001).
4. (в синхроне) Запускаем окружение и процесс для Плеера — делегируем в
   `ModellingService.ensureRunning()` (см. ниже).
5. Финализация обработки запроса:
   - **OK**: Сессия → `PAUSED`, клиенту отправляется номер сессии. Сессия активна,
     занимает ресурсы, поддерживается её жизнеспособность.
   - **ERROR**: Сессия → `CLOSED`, клиенту — причина. Захваченные ресурсы
     освобождаются, порождённые Прикладные сессии уничтожаются.

## `ModellingService.ensureRunning()`

1. Создаст топики в Kafka (для значений и для сообщений).
2. Инициирует Timeline (ячейки данных, которые будут пошагово перекладываться
   в Kafka с заданной скоростью «времени»).
3. Вычитывает и запоминает Стартовый срез данных на начало времени сессии.
   Отправляет срез в созданный набор топиков Kafka.
4. Первично обеспечивает наличие Прикладных сессий (вторичное создание —
   KB-HM-FAULT-001).
5. Настраивает Курсор (положение, скорость).
6. Если сессия в статусе `PLAYING` — запускаются циклы воспроизведения (`tick()`):
   - данные из ячеек Timeline отправляются в набор топиков Kafka;
   - если ячейки Timeline не готовы: воспроизведение приостанавливается,
     данные выгружаются из ClickHouse, когда ячейки готовы — воспроизведение
     продолжается;
   - если скоро закончатся готовые ячейки — предподгрузка на будущие
     (KB-HM-PLAYER-001);
   - на каждой подгрузке очищаются ячейки, оказавшиеся в прошлом.

## Прикладные сессии

В приложениях (hmi-backend, hydro-calculation, alarm-service, alarm-view-service)
произведена доработка для изолированного контекста работы: изоляция от
оперативных данных, изоляция сессий друг от друга.

Прикладная сессия уведомлена про:
- тип сессии;
- её номер;
- какие топики читать;
- какие используются спец-таблицы в ClickHouse;
- в каком теге Сигналов будет размещена информация о движении времени Сессии.

### Время

Про время важно знать, т.к. нужно имитировать появление сигналов в фактическом
прошлом (аналогично про Сообщения). Если Плеер прервал работу, течение времени
должно остановиться и в Прикладных сессиях — это очень важно для
`hydro-calculation` (KB-CALC-MODELLING-001).

### Тег-время

По умолчанию `<Project_Name>:_Player.Time`, тип данных `timeVar`, должен быть
создан и маршрутизирован в Информационной Модели (Redis, KB-HM-STORAGE-001).
